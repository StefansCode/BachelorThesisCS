\section{Softwarearchitektur}

Die geplante Softwarearchitektur sollte nach dem Ports-and-Adapter Pattern 
\cite{cockburn2005hexagonal} aufgebaut sein, allerdings wurden nur 
Adapter implementiert. Die aktuelle Softwarearchitektur ist in Abbildung 
\ref{fig:software_architecture} dargestellt. Ein Pfeil wie bei 
Sound $\rightarrow$ Signal bedeutet, dass Sound Signal nutzt.

Signal ist die Klasse, welche die DSV-Bibliothek implementiert und Sound ist 
eine Erweiterung dieser Klasse, welche ein Audiosignal darstellt.

Diese Architektur hat den Vorteil, dass Sound und Signal unabhängig von der
Hardware sind. Das wird dadurch gewährleistet, dass die 
Zugriffe auf die Hardware nur über Adapter erfolgen.

Synthesizer, Envelope und Menu sind die Komponenten, welche die Hardware und 
Sound nutzen, um einen digitalen Synthesizer zu implementieren. Die genaue 
Funktionsweise wird in Kapitel \ref{chap:synth} beschrieben.

\subsection{Adapter}

\subsubsection{Digital-to-Analog Converter}
Der DAC-Adapter ist eine eigene Komponente dieser Arbeit. Seine öffentliche
Schnittstelle stellt die Methode \lstinline|sendBuffer| bereit. Die Methode
nimmt einen Buffer mit Audiosamples und dessen Länge entgegen. Intern nutzt
der Adapter dafür die I2S-API \cite{esp32s3i2s} der ESP-IDF.

Die I2S-API ist im Standardmodus mit dem Philips-Format eingestellt, da dies
das Standardformat ist, welches der MAX98357A erwartet.

Der Mono-Modus wird verwendet, da der MAX98357A ein Monoverstärker ist.
Das heißt, dass nur ein Signal gesendet wird, anstatt jeweils eins für 
Links und
eins für Rechts. 
% Das I2S Protokoll sendet zwar immer ein linkes und ein 
% rechtes Signal, aber die die I2S-API sendet im Mono-Modus für beide Seiten
% das gleiche Signal und es reicht der API ein Signal zu übergeben.
% Der MAX98357A erhält also immer ein linkes Signal $L$ und ein 
%rechtes Signal $R$ und gibt $(L+R)/2$ verstärkt heraus.

Abtastrate und Auflösung des Signals werden bei der Initialisierung des
Adapters übergeben.

Ein Nutzer des DAC-Adapters, beispielsweise der Synthesizer, ruft zum Senden
eines Signals die Methode \lstinline|sendBuffer| auf. Der Adapter reicht den
Buffer an die I2S-API weiter. Diese wartet bis alle Werte übertragen wurden
und stellt dadurch die konfigurierte Abtastrate sicher.

\begin{lstlisting}[language=C++, 
                   frame=single, 
                   caption={Beispiel Code zum Dac Port},
                   captionpos=b]
Dac dac;
const int bufferLen = 256;
int16_t buffer[bufferLen];
int main() {
    dac.init(32768, 16);
    int16_t value = 0;
    while (true) {
        for (int i = 0; i < bufferLen; i++) {
            buffer[i] = value;
            value++;
        }
        dac.sendBuffer(buffer, bufferLen);
    }
}
\end{lstlisting}

Das Beispiel erzeugt fortlaufend einen Buffer mit 256 Samples und übergibt
ihn an den Adapter. Der Wert 32768 legt eine Abtastrate von 32768 Samples pro
Sekunde fest, während 16 die Sample-Auflösung von 16 Bit angibt. Die
Buffergröße 256 bestimmt, wie viele Samples pro Übertragung an den DAC
gesendet werden. Der Beispielwert wird lediglich zur Veranschaulichung
fortlaufend erhöht; für ein hörbares Signal würde der Synthesizer an dieser
Stelle die berechneten Samples eintragen.

\subsubsection{Button}
Der Button-Adapter bietet zwei Methoden, um auf die Taster zu reagieren
und nutzt intern die GPIO-API \cite{esp32S3gpio} der ESP-IDF.

An \lstinline|getState| wird eine GPIO-Pinnummer übergeben. Als
Rückgabe gibt sie 1 zurück, wenn der Pin mit dieser Nummer LOW ist, 
also wenn der Taster an diesem Pin gedrückt wird. 
Ebenso gibt \lstinline|getState| 0 zurück, wenn der Taster nicht gedrückt ist.

Diese Methode ist dafür geeignet um zu sehen, ob ein Taster über längere
Zeit gedrückt wird. Um nur zu schauen, ob ein Taster kurz oder überhaupt
gedrückt wurde, ist \lstinline|readQueue| die bessere Wahl.

Bei jedem Drücken eines Tasteres, also bei jeden Fallen von HIGH 
zu LOW an einem Pin mit einem Taster, wird die Nummer des Pins 
in eine Queue gepackt.
Die Queue kann mit \lstinline|readQueue| ausgelesen werden.
Hierbei gibt es zwei Dinge zu beachten:

\begin{enumerate}
\item Entprellung. Wenn ein Taster gedrückt wird, geht der Pegel des 
zugehörigen Pins nicht einfach auf LOW, sondern springt ein paar mal 
zwischen LOW und HIGH. Um ein mehrfaches Lesen des Tasters bei
einmaligem Drücken zu verhindern wird zwischen 2 Eingaben 
ein Mindestzeitabstand von 200ms festgelegt.

\item Thread-Sicherheit. Wenn zum Beispiel Taster 1 gedrückt wird und in 
2 verschiedenen Tasks 
\lstinline|readQueue| aufgerufen wird, dann erhält nur einer der beiden Tasks
den Wert 1 und leert die Queue.
\end{enumerate}

\subsubsection{Encoder}
Encoder ist der Adapter für den Drehgeber. Dazu wurden aus dem 
ESP-Beispielcode \cite{espEncoder} für Encoder die wichtigsten Teile kopiert.
Dieser nutzt die Pulsecontrol-API. 

Der Encoder-Adapter hat eine Funktion \lstinline|getValue|, welche ein Wert 
zurückgibt. Dieser Wert ist zu Begin 0 und erhöht sich um Eins, wenn der 
Drehgeber um einen Schritt im Uhrzeigersinn gedreht wurde. 
Gegen den Uhrzeigersinn verringert sich der Wert.

Mit \lstinline|resetValue| wird der Wert auf 0 zurückgesetzt.
% Das ist nötig, wenn Encoder zum Ändern einer Variable genutzt wird,
% aber zwichenzeitlich auch für etwas anderes.
Um eine Variable zu ändern, kann in einer Schleife der aktuelle Wert mit
dem Wert aus der vorherigen Iteration verglichen werden.
Je nachdem, wie sich der Wert ändert, wird die Variable geändert.

\begin{lstlisting}[language=C++, 
                   frame=single, 
                   caption={Beispiel Variable ändern mit Encoder},
                   captionpos=b]
    int lastValue= 0;
    int Variable;
    while(1) {
        if(lastValue < encoder.getValue()) { 
            Variable++;
        }
        if(lastValue > encoder.getValue()) {
            Variable--;
        }
    }
\end{lstlisting}

Dieses Pattern wird häufig mit einer oberen und unteren Grenze verwendet.
Deshalb gibt es in Encoder eine Funktion changeExternalVariable,
welcher man eine Variable ein Minimum, ein Maximum und eine 
Schrittweite gibt. Die Schrittweite gibt an um wieviel die 
Variable erhöht wird.


\subsubsection{Screen}

Der Zugriff auf den OLED-Bildschirm erfolgt über eine Bibliothek
von voidlooprobotech \cite{voidloop2026ssd1306}. Diese
Bibliothek wurde verwendet, weil sie die für das eingesetzte SSD1306-Display
benötigte Initialisierung und die grundlegenden Zeichenoperationen bereits
bereitstellt.

Der Screen-Adapter kann mit Methoden mit dem Präfix \lstinline|draw| 
Punkte, Strings, Zahlen oder Bitmaps auf dem Bildschirm darstellen.

Bitmaps sind uint8\_t-Array, wobei hier jedes Bit ein Pixel darstellt.


\subsubsection{Util und Timer}
Zwei weitere Adapter sind Util und Timer.

Util implementiert die von Arduino bekannten Funktionen \lstinline|millis|
und \lstinline|delay| \cite{arduinoMillis,arduinoDelay}. Außerdem wird die 
Methode micros() implementiert, welche die Anzahl der Mikrosekunden seit dem 
Start des Programms zurückgibt. Diese Funktion wird in Kapitel 
\ref{chap:Bewertung_der_Auflösung_und_Abtastrate} verwendet, um die Ausführzeit
bestimmter Funktionen zu messen. 

\lstinline|delay| hält eine Aufgabe für eine festgelegte Zeit an und
kann beispielsweise verwendet werden, um zwischen zwei nicht zeitkritischen
Display-Aktualisierungen zu warten.

Timer ist ein Wert, der bei 0 startet und alle 16 ms inkrementiert wird.
Die Funktion getValue gibt diesen Wert zurück und setValue setzt den 
Wert auf einen beliebigen Wert.
Das Zeitintervall von 16 ms wird bei der Berechnung der Hüllkurve verwendet
(siehe Kapitel \ref{chap:envelope_calculation}). Beispielsweise kann ein
Task den Timerwert regelmäßig abfragen und bei jeder Erhöhung die nächste
Stufe einer Hüllkurve berechnen. Eine mögliche Erweiterung wäre, das
Inkrementationsintervall bei der Initialisierung zu konfigurieren.

\subsubsection{RGB-LED}
Es wurde ein Adapter für die  RGB-LED auf dem ESP32-S3-Board implementiert.
Dieser Wurde nie genutzt, aber er steht für mögliche Erweiterungen zur Verfügung.

\subsection{Kern}

Der Kern der Anwendung besteht aus 3 Komponenten. Das sind
\begin{enumerate}
    \item die DSV-Bibliothek, welche
            wie oben beschrieben, als eine Klasse namens Signal implementiert ist.
    \item Eine 
            Erweiterung dieser Klasse namens Sound, welche ein Audiosignal darstellt.
    \item Der Synthesizer, welche die Soundklasse nutzt, um mithilfe der 
        Hardware einen Synthesizer zu implementieren. 
        Dazu gehören auch Envelope und Menu.
\end{enumerate}
Diese 3 Komponenten werden in den folgenden Kapiteln beschrieben.
